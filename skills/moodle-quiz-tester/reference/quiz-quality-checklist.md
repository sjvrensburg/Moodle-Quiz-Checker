# Moodle quiz quality checklist (authoring-tool independent)

Distilled from the `moodle-exams-quiz` skill's pitfalls-and-conventions
reference. That skill's checklist is written for the R/exams workflow; this
version keeps only what's actually about **Moodle's own XML/cloze format** or
**general assessment design**, so it applies to a quiz XML from any source —
hand-authored, exported from a live Moodle course, or generated by a
different tool entirely. Use `moodle-quiz-tester` (`mqt-cli`/the HTTP API) to
check the format-level items mechanically; the design items need a human (or
agent) read-through of the rendered questions.

> **Automation note:** most format-level checks below are now enforced
> mechanically by `mqt-cli lint` (missing correct answers, select-all free
> credit, match-everything wildcards, `\[...\]` delimiters, missing/shared
> attachments, malformed cloze blanks, unsupported types, chance-score
> baseline) and the randomisation check by `mqt-cli compare`. Run those
> first; use the manual instructions here only to understand a finding or to
> check something the linter can't see. The design-level and rubric sections
> always need a human/agent read-through.

## Format-level checks (mechanical — grep the XML or inspect parsed JSON)

### Cloze multichoice display: prefer `MULTICHOICE_V`/`MULTICHOICE_VS`
Moodle's cloze format offers both an inline-radio style (`MULTICHOICE`,
`MC`) and a vertical-radio style (`MULTICHOICE_V`, `MCV`) as well as a
dropdown style (`MULTICHOICE_VS`, plain `MC` in some renderers). Long,
sentence-length options collapsing into a narrow `<select>` dropdown make a
question harder to read than intended — verify the rendering choice matches
intent, not just whatever the generator defaulted to.
**Check with this tool:** import the quiz, `show <quiz-id>`, and confirm each
cloze item's `kind` is `MULTICHOICE_INLINE` vs `MULTICHOICE_DROPDOWN` as
intended; or grep the raw XML: `grep -oE '\{1:[A-Z_]+:' *.xml | sort -u`.

### No unescaped `~` inside cloze option text
Moodle's cloze syntax uses `~` as the option separator inside
`{n:TYPE:opt1~opt2~...}` and does not escape a literal `~` in option text —
one slipping in (e.g. from a copy-pasted formula or a stray tilde in prose)
silently splits one option into two, corrupting the answer list.
**Check with this tool:** `show <quiz-id>` and, for every cloze item, count
`options.length` against how many options the question's prose/rubric says
there should be — an unexpected extra option is the signature of this bug.

### Math delimiters: `$...$` / `$$...$$`, never `\[...\]`
Moodle's MathJax filter strips a bare `\[`/`\]` delimiter, leaving literal
bracket characters in the rendered question instead of a formula. Any
question text containing `\[` or `\]` outside of prose (as opposed to inline
`$...$` or display `$$...$$`) needs fixing at the source.
**Check with this tool:** grep the parsed `question_text` (or raw XML) for
literal `\[`/`\]`.

### `exsolution`/blank-type/tolerance count parity (cloze)
Every cloze blank needs a consistent type, solution, and tolerance entry —
in the source `.Rmd`/generator this is three `|`-separated strings that must
have equal element counts; in the rendered XML it surfaces as each
`{n:TYPE:...}` marker needing a matching, well-formed option list.
**Check with this tool:** `show <quiz-id>` and confirm `cloze_items.length`
equals the number of `{n:...}` markers you count in the question prose, and
that no item has an empty `options` list.

### Embedded attachments actually present
If question text (or the export) mentions a downloadable dataset/script
(commonly via `@@PLUGINFILE@@/filename`), the corresponding `<file>` element
must exist in the XML — a broken/missing attachment fails silently for a
student who can't complete the question.
**Check with this tool:** `show <quiz-id>` and confirm `files` is non-empty
for every question whose prose references a filename.

## Design-level checks (need a human/agent read-through)

### No 1-mark non-MCQ items
Every non-MCQ question or subpart should be worth ≥ 2 marks; 1-mark
short-answer/numerical items create disproportionate partial-credit grading
noise relative to their weight. Fold a naturally-1-mark sub-task into an
adjacent part instead.

### Proofs and multi-step arguments as single blocks
A multi-mark proof or derivation reads better as one question with an
internal roadmap ("Your answer should: (i)…, (ii)…, (iii)…") than as several
small subparts — subparts lock the student into one argument order and can
break the logical flow of a derivation. Reserve subparts for genuinely
independent content.

### No answer leakage across the quiz
No question's setup, feedback, or general-feedback text may leak the answer
to a *different* question. State any modified setup via its own
self-contained description, not by cross-referencing another question's
numbered assumptions or answer. Read every question against every other
question (and against any shared formula sheet/reference material) before
publishing.

### Subpart / blank independence
A student who gets one part wrong must still be able to attempt the next —
every blank/subpart should be computable from the given data and question
text, not from an earlier blank's numeric result. If part (b) genuinely
requires part (a)'s output, merge them into one question rather than
chaining grading dependencies (sequential proofs are the natural exception).

### Reference-material hygiene
Any formula sheet or reference material distributed with the quiz should
list only general building blocks, never a formula that is itself the
punchline answer to a question in that same quiz.

### Scaffolding gives hints, not answers
Any placeholder/scaffolding text (a fill-in-the-blank comment, a "hint"
field, general feedback shown before full completion) should point at the
relevant concept, function, or reference — never contain the literal
expression that fills the blank. Litmus test: if copy-pasting the hint
directly into the blank produces a correct, complete answer, it's not a
hint, it's the answer.

### Consistent notation/terminology
Use one consistent notation and terminology throughout the quiz (and
matching whatever course material the students study from) rather than
mixing textbook conventions — forcing students to mentally translate between
the quiz's wording and their notes costs time disproportionately and isn't
part of what's being assessed.

### ESL-friendly wording
Assume the cohort includes second-language English speakers: prefer plain,
direct sentence constructions over nested clauses or jargon-heavy nouns, and
avoid phrasing that reads like a template with a fillable slot unless it's
clearly marked as such (e.g. an explicit placeholder function/marker, not a
bare blank).

### Independent, uniquely-scoped applied/data questions
Within one quiz, no two applied (dataset-driven) questions should share a
downloaded dataset or script filename, and no question's scenario should
depend on "continuing from" a previous question — Moodle randomises question
order and (for question banks with multiple versions) pools versions
independently, so a shared file or an assumed prior answer makes correctness
depend on state the student may not actually have. Each applied question
needs its own self-contained scenario and its own uniquely-named
attachment(s), if any.
**Check with this tool:** `show <quiz-id>` and diff the `files[].name` lists
across all questions — any filename appearing under more than one question
is a violation (unless it's genuinely one merged scenario deliberately split
into multiple graded blanks of the *same* question, which is fine).

### Randomised items must actually vary where they're supposed to
For any quiz drawn from a question bank with multiple randomised versions of
the same item, a fresh random seed doesn't automatically make every blank's
answer vary — two common failure modes:
- **Trivial arithmetic from fixed constants** (e.g. a count computed from
  two hard-coded numbers) is identical across every version regardless of
  seed.
- **Self-referential construction** (e.g. a class label built from a
  quantile of the same randomised data it's later compared against) can pin
  a derived answer — like a baseline accuracy — to the same value in every
  version even though the underlying data differs.
Verify by generating/pulling several versions of the same item and diffing
their answer keys column-by-column; a constant column is only fine if it's
the deliberate teaching point (a fixed reference value, a mathematical
constant, a genuine model invariant).
**Check with this tool:** `mqt-cli compare bank.xml` (one file, versions
grouped by question name) or `mqt-cli compare v1.xml v2.xml ...` — flags any
answer-key column constant across every version.

## Distractor and feedback rubric (MCQ craft — needs an agent/human read)

Where agent-generated quizzes are most reliably mediocre. Apply to every
multichoice/truefalse question and every multichoice cloze blank.

### Every distractor encodes a nameable misconception
For each wrong option you must be able to state the specific error a student
would make to arrive at it ("forgot to square the deviation", "used n instead
of n−1", "confused correlation with slope"). If you can't name the error, the
option is filler — it lowers the guessing denominator without measuring
anything. Replace it with a computed wrong answer: work the problem with each
anticipated mistake and use those results as the distractors.

### Options are homogeneous
Same grammatical form, comparable length and detail, consistent precision
(all 2 d.p., or all round). The correct answer must not be identifiable as
the longest, most qualified, or oddly-precise option. (The adversarial
protocol's test-wise pass is the empirical check for this.)

### No throwaway aggregate options
"All of the above" / "none of the above" are almost always the weakest
choice: when correct they reward partial knowledge, when wrong they're
transparent filler. Prefer a real fourth distractor. If used, they must be
the correct answer roughly as often as any other position across the quiz.

### Wrong-answer feedback teaches
Per-option feedback on a distractor should name the misconception and point
the way ("This is the result of using n instead of n−1 — see the sample
variance definition"), not merely restate wrongness ("Incorrect."). A student
reading only the feedback for their wrong choice should know *what to
review*, without being handed the correct answer outright (which matters when
multiple attempts are allowed).

### Correct-answer feedback confirms the reasoning, not just the fact
One sentence of *why* the answer is right consolidates learning; a bare
"Correct!" wastes the moment. For numerical/computed answers, show the key
step or formula in the general feedback.

### General feedback is a worked path
For computed questions, general feedback (shown to everyone after the
attempt) should sketch the worked solution or name the exact
concept/reference section, so the quiz functions as a study object after
grading — while respecting the answer-leakage and scaffolding rules above
for anything shown *before* completion.
